# U22 — Real-runner verification checklist

Written by the developer (Sonnet, this unit). **The orchestrator runs this** after the
user creates the GitHub org/repo (decision 1 in `units-of-work.md`'s "Decisions only the
user can make") and fills in the evidence column below. Nothing on this list is
"verified" until its evidence is pasted into `aidlc-docs/audit.md` — none of it can be
proven from a worktree with no real GitHub Actions runner, which is why it's a checklist
and not a test in this repo.

Do not run any of this yet. No org exists; no repo has been pushed. This file is the plan
for the orchestrator to execute once G7's blocking user decisions (1–3) are made and the
repo exists.

## How to run each item

| # | Check | How | Evidence to capture | If it fails |
|---|---|---|---|---|
| 1 | `ci.yml` build job green | Push to the new repo (or open a PR) and watch the `build` job: checkout, install, lint, typecheck, test, leaderboard diff-check. | Paste the job's duration and a link to the run. | Fix the underlying failure before proceeding — don't touch this checklist to route around it. |
| 2 | `*.localhost` resolves on `ubuntu-latest` | Watch the `host-resolution` job (`.github/workflows/ci.yml`): `getent hosts x402rt-probe.localhost`, a Node `dns.lookup`, a Python `socket.getaddrinfo` (all three asserting a loopback address), and the real `preflightHostMode("localhost")` function itself. | Paste all four steps' output, including the resolved address **and address family** (IPv4 `127.0.0.1` vs IPv6 `::1` - see item (e) below) from the Node/Python steps. | **Stop and escalate to the architect.** `host_mode: localhost` cannot be the canonical default on these runners. The fallback is ADR-012's proxy mode, or adding an `/etc/hosts` step to `action.yml` before the harness runs — don't pick one yourself; this is a contract-level decision. |
| 3 | E2E shards green, each under 60 min | Watch the `e2e` job's matrix shards (`corpus-v2`, `driver-calibration`, `guardrail-integrity`, `hosts`, `rpc-capture`, `run-suite` - `packages/cli/test/action-yaml.test.ts` keeps this list in sync with the real `*.e2e.test.ts` files, so trust the matrix as-run, not this list, if they ever diverge). | Paste each shard's duration from the Actions UI. | Any shard over ~45 min (budget margin): split that file's own test suite further, or move its slowest tests into a new shard — update the matrix list in `ci.yml` to match (the sync test will catch a forgotten update). |
| 4 | Self-test: all six exact exit codes | Watch `.github/workflows/self-test.yml`'s `exact-exit-codes` matrix: naive→1, guarded→0, `"true"`→2, guardrail allow-all→1, guardrail deny-all→2, guardrail reference-policy→0. Each case asserts the action's `exit-code` *output*, not the step's `outcome`. | Paste the six `OK: <case> exited <n> as expected` lines (or the failing `::error::` line and the actual outputs/logs if one doesn't match). | A mismatch is a real regression in `packages/cli/src/run.ts`'s `computeExitCode` or in `action.yml`'s plumbing — don't adjust the expected value to make it pass; find why the exit code changed. |
| 5 | SARIF upload works with only `security-events: write` | On a workflow/job granting exactly `permissions: security-events: write` (nothing broader), run the action with `upload-sarif: true` against a scenario with at least one failure, then check the repo's Security → Code scanning tab. | Screenshot or the `GET /repos/{owner}/{repo}/code-scanning/alerts` API response showing the `x402-redteam` category's findings. | If it needs more than `security-events: write`, that's a contract bug in `action.yml`'s "Upload SARIF" step or the `github/codeql-action/upload-sarif` version pinned there — report to the architect before loosening permissions to make it pass. |
| 6 | `rank.yml` attestation + verification (U19) | From a throwaway **public** test repo running `examples/guardrails/reference-policy.ts` through `rank.yml`, then `gh attestation verify --signer-workflow <rank.yml's workflow path>` against the produced `report.json`. Separately, hand-edit one byte of a downloaded `report.json` and re-verify — it must fail. | Paste the `gh attestation verify` success output, and the tampered-file failure output. | This is U19's workflow, not U22's — escalate to U19's owner/the architect, not this checklist. |
| 7 | `ranked-run.yml` dry run, dummy season (U19) | Dry run with a **test** seed and a 3-scenario dummy held-out corpus (never the real Season 1 corpus). Confirm inside the run: (a) the container has no network — `curl` fails; (b) the agent's uid can't read the corpus path; (c) the seed string appears in **no** log or artifact; (d) only the redacted report and the attestation are uploaded (not the raw `report.json`, not `runs/*.json`). | Paste the `curl` failure, the permission-denied read attempt, a `grep -r <seed>` over every uploaded artifact (must return nothing), and the artifact listing. | A real seed or corpus leak here means the Season 1 corpus is compromised before it's ever used — do not proceed to the real season under any circumstances; escalate immediately. |
| 8 | Python agent on the runner, localhost mode, EVM | Run `examples/agents-py`'s agent (uv venv, EVM, header-only) through the action in `host-mode: localhost` on `ubuntu-latest`. | Paste the run's `report.json` summary and confirm `config.host_mode` is `"localhost"` (not a silent fallback to `"path"`). | If it silently fell back, that's item 2 failing quietly — go back and fix item 2 first; this item can't pass meaningfully until that one does. |
| (a) | Per-matrix artifact upload doesn't collide | Run `self-test.yml`'s `exact-exit-codes` matrix (or any workflow using `guardrail`/multiple legs in one job) and check the run's Artifacts list. | Paste the artifact list showing six distinctly-named `x402-redteam-report-<case>` artifacts (one per matrix leg), no "artifact name already exists" failure. | If two legs collided, a workflow is reusing `artifact-name` (or omitting it) across legs that should each set their own — fix the workflow, not `action.yml`. |
| (b) | No-report path: `agent` and `guardrail` both set, and both unset | Run the action once with both `agent` and `guardrail` given, and once with neither. | Paste both runs' `exit-code` output (must be `2` both times, per `main.ts`'s own validation) and every other output (`valid`, `safety-score`, `reach-rate`, `pass-rate`, `unauthorized-usd`) — must all be the **empty string**, never `"null"` or `0`. Also confirm the step summary shows "no report was produced" with the harness's own usage-error text, not a blank summary. | If any numeric output reads `0` or `"null"` instead of empty, that's a regression in the `run:` step's Node output-writer (action.yml) — re-check it reads `summary` only when `JSON.parse` actually succeeded. |
| (c) | Fork / no-permission SARIF run doesn't fail the job | Open a PR from a fork (or a job deliberately granted only `contents: read`, no `security-events: write`) with `upload-sarif: true` and at least one real failure (so `report.sarif` is written). | Paste the SARIF upload step showing a failure icon but the job overall still reflects the harness's own exit code (i.e. the job fails *only* if the harness itself returned non-zero, never *because* the SARIF step failed). | If the job fails purely because of the SARIF step (no `continue-on-error`, or a missing `if: always()` on a later step), that's a regression in `action.yml` — re-check both of those against the current file before changing anything else. |
| (d) | `--pass-env` canary doesn't survive into the downloaded artifact | Run the action with `pass-env: SOME_NAME` set to a long (>=8 char), unique canary value, against an agent that deliberately echoes its own env (a throwaway test agent, not one of the repo's reference agents) with `include-agent-logs: true` (so the scrub is actually exercised, not just skipped by exclusion). Download the resulting artifact. | Paste a `grep -r "<canary value>"` over the unzipped artifact - must return **no matches**. If it does, also paste the literal match and which file it was in. | A match is a real secret-leak regression in `packages/cli/src/spawn.ts`'s `scrubSecretsFromLog` or its call site in `run.ts` - treat as urgent; don't publish any artifact from a real run until fixed, and re-run every item on this checklist that produced one in the meantime. |
| (e) | Loopback address family recorded | From item 2's Node/Python steps, note whether the probe resolved to IPv4 (`127.0.0.1`) or IPv6 (`::1`) - ubuntu-latest's resolver order can pick either. | Paste the family alongside item 2's evidence; if it's IPv6, separately confirm the adversary's own loopback HTTP server binds dual-stack (or note that it's IPv4-only and `*.localhost` must resolve to `127.0.0.1` specifically on these runners for the probe's real HTTP round trip to succeed - see `packages/cli/src/host-env.ts`'s `probeLoopbackGet`, which binds `127.0.0.1` explicitly). | If the resolved family and the probe server's bound family don't match, that's exactly the kind of failure item 2 exists to catch before `host_mode: localhost` ships as the default - escalate per item 2's own "if it fails" column, don't patch around it here. |
| (f) | The action's own outputs are populated even when the composite itself reports a failure | Deliberately provoke an internal step failure that isn't the harness's own result - e.g. run with `upload-sarif: true` on a job with no `security-events: write` permission, so the "Upload SARIF" step fails. | Paste `exit-code`/`valid`/`safety-score`/`reach-rate`/`pass-rate`/`unauthorized-usd` from that run's outputs, showing they're still the harness's real values (not empty, not stale) despite the SARIF step's own failure; separately, run the same case with `exit-on-result: false` and confirm the *job* is green while `exit-code` still correctly reports the harness's non-zero result. | If outputs come back empty/stale when an unrelated step fails, that's a regression in the `if: always()` chain (action.yml) - an output's `value:` always reads the "Run x402-redteam" step's own outputs regardless of later steps, so re-check nothing upstream of it was skipped. |

## Notes for whoever runs this

- Items 1–5 and (a)–(c), (e)–(f) only need the public repo to exist and Actions enabled —
  no secrets, no season, no `ranked` environment.
- Items 6–8 need more of decision 1 (the `ranked` environment, a throwaway public test
  repo) and decision 2 (a seed, even a disposable test one) from `units-of-work.md`.
  Don't improvise a seed or a "temporary" season — use a value explicitly marked as a
  throwaway test fixture, never anything that could later be mistaken for Season 1's
  real secret.
- Item (d) needs a throwaway test agent that deliberately echoes its own env - write one
  as a one-off, outside `examples/agents/` (none of the repo's reference agents do this
  on purpose), and delete it after - it's a fixture for this one check, not a permanent
  addition.
- Record every result (pass or fail) in `aidlc-docs/audit.md`, append-only, with links/
  durations/output exactly as captured above — not a summary of "it worked."
- This file is owned by U22 per `units-of-work.md`'s Bolt 6 ownership table. If an item's
  mechanism changes (e.g. the e2e shard list in `ci.yml`), keep this checklist's "How to
  run each item" column in sync in the same change.
